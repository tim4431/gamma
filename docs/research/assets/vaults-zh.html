同步仓库与原地阅读

一个功能，同步仓库：Gamma 里的文件夹或页面与这台电脑上的目录或文件之间的一条关联，按设定的方向拉取、推送或两者都做；你自己的 Markdown 与 PDF 目录由此像 Obsidian 仓库（vault）那样在 Gamma 中双向编辑。以及在 PDF 所在之处直接阅读它，不必先加入文库。

问题与答案

可以，条件只有一个：对你自己的目录，凡是文件能表达的，以本地文件为准；Gamma 写文件只对它上次读到的字节打补丁，绝不重新渲染整个页面。功能只有一个，同步仓库：Gamma 里的东西与这台电脑上的东西之间的一条关联，有范围（文件夹与目录，或页面与一个文件）和方向（拉取、推送或两者）。「保存到这台电脑」原是只拉取的仓库，「跟随文件」原是只有一个文件、只推送的仓库（下称单文件仓库），你自己的目录是两个方向都同步的仓库。从任何地方打开的 PDF 都在原处读取，你要求时才成为文库页面。

笔记要回答三个问题

  1. Gamma 能否像 Obsidian 对待仓库那样，双向处理一个本地的 Markdown 与 PDF 目录，而且永远不损坏文件？
  2. 能否读取任意一个 PDF 并就它聊天，而不把它加入文库？
  3. 文件装不下的东西，都放在哪里？

用 git 的话说，界面里也这样说

远端

本地
这台电脑上的目录或文件

Gamma 的改动写到磁盘
推送

界面里从不出现的 git 词：克隆（clone，在 Gamma 里已指另一台服务器上工作区的副本）、提交、分支、抓取、贮藏。唯一没有 git 对应物的：回收站（.gamma/trash/）。

已决定（2026-11-06）

  1. 仓库是一个文件夹，不是工作区普通工作区里与某个目录绑定的一个文件夹；多个仓库就是同一文库里的多个文件夹。这是项目负责人的选择，与笔记最初的建议相反。随后确认：「保存到这台电脑」和「跟随文件」也符合同一模型，仓库不是第三种关联。
  2. 建立关联时在目录里写入 .gamma/仿照 Syncthing 的标记：一个隐藏目录，里面有一个文件；它不在，关联就停止。这个文件还带一个 ID，与 Resilio 的做法一样。
  3. 交给应用的 PDF 在原处读取加入文库是第二步，需要明确要求。
  4. PDF 的笔记放在它旁边，同名除非仓库设置指定了笔记文件夹。Obsidian 在这里没有可循的规则；在别处、以 source 指向该 PDF 的笔记同样有效。
  5. Markdown 无法表达的留在 Gamma 的数据库高亮的矩形区域、手写、文本框。不用旁车文件（sidecar）。这是 Zotero 和 Sioyek 的选择。
  6. 一个功能，叫同步仓库取代「保存到这台电脑…」和「跟随这台电脑上的文件…」。两者都成为设定了方向的同步仓库，都不再有自己的名字。
  7. 用 git 的词，界面里也用Gamma 服务器永远是远端，这台电脑上的目录或文件是本地。拉取把 Gamma 的改动带到磁盘，推送把磁盘的改动送进 Gamma。副本的设置已经这样说。
  8. .gamma/ 属于目录，从不属于文件单文件仓库旁边什么都不留；同一目录里有几个这样的文件，也什么都不留，对话框会提议改为同步整个目录。

一个功能：同步仓库

Gamma 与这台电脑之间的每一条关联都是一个同步仓库：没有第三种，也不再是两种。仓库就是范围加方向。范围是文件夹 ↔ 目录，或页面 ↔ 一个文件；方向是拉取（Gamma → 磁盘）、推送（磁盘 → Gamma）或两者。今天的两个功能只留下旧名，它们是这个功能的两种设置。

范围：文件夹 ↔ 目录
范围：页面 ↔ 一个文件

目录仓库有两个开关：拉取开或关；推送关、仅 PDF 或全部。旧名都只是这两个开关的设置，现有的 push 列本来就是这个意思。建立时总有一侧是空的：从有页面的文件夹和空目录开始，或从目录和新文件夹开始；此后只靠方向区分。单文件仓库只有推送一个开关，从不提供拉取：Gamma 绝不写它没放进去的 PDF。Syncthing 给文件夹的也是这三种方向：仅发送、仅接收、发送与接收。

原来叫范围拉取（Gamma → 磁盘）推送（磁盘 → Gamma）怎样开始
「保存到这台电脑…」现有文件夹 ↔ 目录开关；或仅 PDF一个文件夹，一个空目录
仓库计划 · 第 3 步文件夹 ↔ 目录开全部：笔记、PDF、新文件、重命名、删除一个目录，一个新文件夹
只读仓库计划 · 第 2 步文件夹 ↔ 目录关全部一个目录，一个新文件夹
「跟随这台电脑上的文件…」现有页面 ↔ 一个文件从不这个 PDF，存入 Gamma页面的「文档」菜单
打开的 PDF（阅读器）计划 · 第 1 步页面 ↔ 一个文件从不这个 PDF，原地读取「打开方式」；添加到文库时选了继续推送，才成为一行仓库

界面用语

界面到处用同样几个词，也就是副本设置（SettingsMirrors.jsx）已经在用的：正在拉取、正在推送、强制拉取、强制推送、未推送的编辑。git 的其他词在这里没有意义，从不出现：克隆已指另一台服务器上工作区的副本，也没有什么会被提交、建分支、抓取或贮藏。中文用 git 自己的译法：拉取、推送、冲突；vault 用 Obsidian 自己的中文「仓库」（它的帮助里写「打开其他仓库」「新建仓库」），所以叫同步仓库，git 的中文也把 repository 叫仓库。

词意思出现在
同步仓库、仓库Gamma 与这台电脑之间的一条关联，有范围和方向功能的名字：同步面板的分区、设置搜索、用户指南
远端仓库所属的 Gamma 服务器和工作区；总写服务器的名字，从不单写“远端”仓库的那一行：D:\Papers ⇄ NAS · Research / Papers
本地这台电脑上的目录或文件同一行、对话框
拉取Gamma → 磁盘：页面成为文件，改名就移动文件，删除就把文件移进回收站对话框的「拉取」开关、「立即拉取」、「正在拉取」、「已拉取 12 个文件」
推送磁盘 → Gamma：文件成为页面，或成为页面的新 PDF开关「推送：关 / 仅 PDF / 全部」、「立即推送」、「正在推送」、「3 项待推送」
同步先拉取再推送，开着哪个就做哪个「立即同步」、30 秒定时轮询、CLI 的 sync
已是最新没有要拉取或推送的行的状态，与副本一样
冲突上次同步之后，一个块或一个 PDF 两边都改了；文件为准，Gamma 一方保留「1 个冲突」、块上的合并提示
未跟踪目录里 Gamma 不读的文件：不认识的类型、忽略列表里的「未跟踪：4 个文件」，在仓库的状态里，从不在文库里
强制拉取、强制推送说明数量、经你确认后，用这一侧替换另一侧的改动行的菜单，与副本的「强制拉取」「强制推送」在同一处
移除仓库关联去掉；文件保留或移进回收站，按你的选择；页面保留行的菜单，带这两个选项

单文件仓库是最小单元

只同步一个文件，也有 .gamma 吗？

没有。.gamma/ 属于目录，从不属于文件。标记回答的是目录才有的两个问题：这还是同一个目录吗（一个空着的挂载点不是一个被清空的仓库）；Gamma 可以在这里写吗。单文件仓库两个问题都没有：Gamma 从不在文件旁边写东西；文件不见了，只是页面的文件「缺失」，页面绝不因此被删除。

一个文件：磁盘上什么都没有关联存在 Gamma 的数据库里，像 Zotero 的关联文件：路径、哈希、大小和时间、文件 ID。它所在的目录不读，旁边的文件不是任何人的页面。
同一目录里几个文件：仍然什么都没有每个都是自己的仓库，有自己的页面，归在各自的位置。再添加一个时，对话框只提示一句：D:\Papers 中已有 3 个文件逐个同步，改为同步整个文件夹？
目录成为仓库，就吸收里面的单文件仓库每个页面保留它的 ID、笔记和批注，归入与文件所在目录对应的文件夹，原来的归入位置也保留；它自己的那一行去掉。反过来会被拒绝，因为仓库互不重叠：仓库目录里的文件已经是一个页面，「文档」菜单会打开它。
目录仓库总有标记，不论方向只推送的仓库也写入 .gamma/，别无其他，并事先说明：分辨拔掉的盘和被清空的盘靠的就是它，而要回答这个问题的，正是推送的那一侧。Syncthing 在“仅接收”文件夹里也写 .stfolder，理由相同。

今天的关联为此改变的

  • 渲染器。能推送的仓库，需要解析器能把文件还原成同一棵树，所以笔记改由透镜的编码器写出，不再用 render_vault_page。Gamma 自己的文件按这种方言重写一次；磁盘上改过的照旧保留。
  • 状态文件。.gamma-sync.json 让位于 .gamma/ 里的标记和数据目录里的合并基准；gamma-sync 客户端没有数据目录，保留自己的。
  • gamma_id。由合并基准说明一个路径是哪个页面；文件里有这一行仍会读取，但不再写入。
  • 单向命名。标题仍决定文件名；开启推送后，文件名也决定页面标题。
  • 名字。两个菜单项、面板的用词和指南的两节，按上面的用语重写；folder_links 还是那些行，kind 读作范围。

有意保留的

  • 只拉取是一个承诺，不是要长大脱离的阶段。人们把带批注的文件放进只拉取的文件夹，正是相信它们不会回到 Gamma。这样的仓库在磁盘上发现的改动会保留并报告，绝不推送；强制拉取会替换它，就像 Syncthing 的“仅发送”文件夹在“覆盖更改”之前不理会另一端。推送要明确开启，就像现在推送 PDF。
  • 通过 HTTP 推送全部内容以后再做。今天 NAS 上的文件夹只靠读取就能拉取到 PC；推送笔记和新文件，需要带写令牌发送它们的操作（第 5 步）。
  • 存入还是原地读取，是存储的问题，不是仓库的问题：服务器在这台电脑上、并在这里找到了文件，就原地读取；否则存入。

原文 · A vault is a folder

仓库的唯一规则

仓库文件夹下的页面和仓库目录里的文件一一对应。磁盘上的新建、修改、移动和删除推送进 Gamma，Gamma 中的同类操作拉取到磁盘；身份就是路径，文件夹本身的规则一条不改。

归入仓库文件夹之下的页面，就是仓库目录中的一个文件；目录中的文件，就是归入该文件夹之下的页面。

归入照旧：多对多，只检查形状（ops._filing_patch），「移动到文件夹」仍是添加。页面的文件放在哪里，沿用「保存到这台电脑」今天已有的规则：页面在所关联文件夹之下的第一个归入位置。所以没有第二种文件夹，重新归入页面的任何路径也没有新的拒绝。

推送：磁盘上发生的
一个目录一个文件夹
.md / .pdf笔记页面 / 论文，归入其目录对应的文件夹，以文件名为标题。这个标题不是自动标题（auto_title），元数据查询只填论文字段，绝不改文件名；“把文件重命名为论文标题”可以做成一条命令。
文件改了页面跟着改
文件移动了页面在仓库下的归入位置跟着变，其他归入位置不动
文件不见了页面进入「最近删除」
一个路径消失，另一个出现身份就是路径。新文件的文件 ID 或哈希相同，或 PDF 的 /ID 相同（被别的阅读器移动并保存过），就算移动；移动后又编辑过的笔记靠相似度判断。其余都算删除加新页面，删除的页面带着上面的一切等待三十天。
拉取：Gamma 中发生的
在文件夹里新建或归入页面得到它的文件：笔记写成 <dir>/<Title>.md；原先存储的 PDF 复制到旁边，此后跟随
改标题文件改名
仓库下第一个归入位置变了文件移动
仓库内的文件夹改名或移动对应目录改名或移动
页面进入「最近删除」它的文件进入仓库回收站；恢复时文件移回原处
页面失去仓库下最后一个归入位置离开仓库：原地读取的 PDF 先存入，再把文件移进回收站，页面作为文库页面保留，上面的一切都在。在 Gamma 中删除文件夹照常取消其页面的归入，页面按这条离开；目录空了才删除。

拉取得知 Gamma 中的改动，与其他同步的方式相同：先是 ops.notify_commit，再查 page_changes 中该文件夹下的页面和 folders 树。

建立与移除

  1. 「添加同步仓库…」在启动器、桌面栏（bar）和同步面板里，从目录开始（「打开这台电脑上的文件夹…」）
  2. 系统的选择器选定目录
  3. 先扫描并说明找到了什么、将写入什么（标记，别无其他），然后才动手
  4. 新建以目录命名的文件夹放在打开的工作区（若它属于本地服务器、可以有仓库），否则放在主机的个人工作区

已关联的目录总是对应一个新的空文件夹：已有的文件夹和已有的目录不会合并。多个仓库就是同一文库的多个文件夹，无需切换：各仓库的标签页并排，一次搜索覆盖全部（也可限定到某个文件夹），一个仓库里的笔记可以提及另一个仓库或文库里的论文；在文件中，这种提及写成页面的 Gamma 绝对地址，再读取时仍是提及。

移除：「移除仓库…」只问文件怎么办，保留还是移进回收站；从不问页面：页面留下，上面的一切都在。仓库原地读取的 PDF 先存入，免得有页面指向 Gamma 不再监视的路径；动手之前，那一行会说明涉及多少个、多大。不想要的页面，之后像任何页面一样删除。

必须不同的四处，各只改一个地方

  • 一份文档一个页面，在仓库里不成立：两个目录里的同一个 PDF 是两个页面。PDF 为关联文件的页面不参与 blocks_store.page_for_doc，replace_attachment 也不因别的页面持有相同字节而拒绝（HeldElsewhere）。文库照旧：加入文库的 PDF 找到的是文库的页面，绝不是仓库的。
  • 副本或关联了 Zotero 的工作区里不能推送，仓库页面也不发布。镜像只同步 storage.exists 在上传目录里找到的文件，副本会只带走页面、没有 PDF；Zotero 关联会把这个文件夹变成一个分类。只拉取的仓库今天两者都允许，它不往 Gamma 写任何东西。
  • 仓库互不重叠：仓库目录不在另一个仓库的目录之内，也不包住一个；仓库文件夹不在另一个仓库之下。root 或上层文件夹上只拉取的仓库，不包含推送的仓库之下的页面（否则 folder_sync.layout 会把它们的笔记渲染进第二个目录）。归入两个仓库的页面属于第一个，第二个报告并放过它。目录仓库里的单文件仓库会被吸收，见上文“只同步一个文件”。
  • push 今天只读作开或关（run_link、due、tick、路由、desktop/lib/keeping.js）：各处都要学会第三个值（全部），以及关掉拉取、让 Gamma 停止写入的开关。

一切存放在哪里

本地目录里只有你的文件，外加一个 .gamma/：它只相当于 .git/ 里标出“这是一个仓库”的部分，放标记、设置和回收站；目录仓库不论方向都有它，单文件仓库没有。合并基准、历史，以及 Markdown 装不下的批注，都在 Gamma 的数据目录。

为什么放在文件里任何打开这个目录的工具都能读：Obsidian、智能体（agent）、git。
为什么放在 .gamma/标记必须和文件在一起；回收站在同一个卷上，删除就只是一次重命名。
为什么放在数据目录这是 Gamma 自己的数据，用 Gamma 自己的合并和备份；或者是这台设备自己才知道的事。
  • 标记：.gamma/ 隐藏、内含文件，清理工具不会动它（与 Syncthing 的标记一样）。找不到标记或 ID 不对，关联就停止并说明，绝不当成删除。需要 ID 是因为路径不够：目录移动或改名后，把关联重新指向它即可找回，Gamma 先确认是同一个仓库，再与已有页面对接；同一盘符下换了另一块盘会被拒绝。
  • 仓库的文件里没有 gamma_id，仓库里也没有数据库。
  • 块 ID 在第一次读取时生成，由页面保存。只有文件外的东西依赖某个块（一条高亮、一个指向它的链接）时，它才在文件里得到 ^anchor：这是 Obsidian 的习惯，也是仓库导出的规则。
  • 历史属于 Gamma：写入替换掉的内容存在数据目录，就像 Obsidian 的文件恢复、Syncthing 的索引都随应用保存。除了回收站，仓库里什么都不累积。

原文 · Is Gamma a Markdown editor?

Gamma 是 Obsidian 那样的 Markdown 编辑器吗？

一半是。在一个块之内是，而且用的是 Obsidian 自己的引擎；作为一份文档不是：Obsidian 的笔记是一段文本，Gamma 的页面是一个大纲。所以仓库页面是透过大纲编辑的 Markdown 文件，大纲显示不了的，由「编辑文件」补上。

在块之内：是

  • 块的内容就是原样的 Markdown 文本，别无其他：没有 HTML，没有富文本 JSON（markdown_import.py 的说明；db.py 里的 unified_blocks 表）。
  • 编辑器是 CodeMirror 6，与 Obsidian 相同：正在编辑的块里有一个实例（BlockCmEditor.jsx），公式、引用和标记实时渲染，光标所在处显示源码，就像 Obsidian 的实时预览；其他块经 react-markdown 渲染（GFM、公式、标注框、KaTeX）。
  • 这些都按 Markdown 输入，存进去还是 Markdown：**粗体***斜体*`代码`==标记==[链接](…)[[wikilink]]![[图.png|300]]$…$$$…$$```围栏```Mermaid| 表格 |- [ ] 任务> 引用> [!callout]
  • 回车按 Obsidian 的方式延续列表、任务或引用（mdLines.js），/ 命令改写一行的前缀。这些都不需要改。

作为文档：不是

  • Obsidian 的笔记是一段文本，结构就是文本所写的那样。
  • Gamma 的页面是大纲：一行行带父级和位置的块，每一行都画成一个项目符号（BlockTree.jsx）；标题只是文本以 # 开头的块。
  • 文件要变成这个形状，得经过一个导入器，由它决定在哪里切开、怎样嵌套；这些决定两个方向都有损失，见下表。
  • 透镜建成后，习惯 Obsidian 的人仍会注意到三点：每个段落前面都有一个项目符号；嵌在普通段落下面的块，在文件里变成列表；解析器不认识的（HTML 块、setext 标题、跨段落的脚注）是一个不透明块，按文本显示、按文本编辑，不渲染。

所以：仓库页面是透过大纲编辑的 Markdown 文件

透镜建成后，Gamma 里的每一次编辑都是对文件逐字节准确的补丁，在别处编辑过的文件一块一块地到达。大纲显示不了的，由一个源码视图补上：

笔记双向：打补丁，绝不重新渲染

拉取像 git pull：远端的改动打成补丁，应用到本地文件，只动改过的块的字节。推送像 git push：带着合并基准提交，远端做三方合并。两边改了同一处字符就是冲突：本地文件为准，远端的版本保留为冲突记录。

为什么不能沿用现在的笔记文件

今天的笔记文件是渲染出来的，读取它的是导入器。obsidian_export.render_vault_page 会把大纲压平；markdown_import.md_to_blocks 会去掉每行首尾的空白、丢掉项目符号、把制表符换成四个空格、去掉标注框的折叠标记、截掉代码围栏里的行尾空格，没有哪个块记得自己的项目符号或缩进。读一个文件再写出去，得不到原来的文件。做导入这没问题；在这对函数上建同步，会重写它碰过的每一个文件。

双向同步需要的零件倒是都在：带 base 的 set 会三方合并（textmerge.merge）；ops.notify_commit 通知监听者页面变了，page_changes 每页一行记录最新的 seq；磁盘关联已有存储、定时轮询和面板；PDF 变了，高亮会重新定位。

良态透镜（well-behaved lens）的两条定律

第一条读了再写，什么都不变Gamma 没编辑过的文件绝不写入；对一个块的编辑只改变这个块的字节。
第二条写了再读，还是同一棵树否则 Gamma 自己的写入会在下次读取时被当成改动，两边互相追逐。

渲染器要满足第一条，就得对所有写过的文件都完美无缺；打补丁则天然满足。

区段（span）与外壳（dress）

  • 解析器不认识的东西（setext 标题、HTML 块、缩进代码、引用定义）成为一个不透明块，内容就是它的区段。
  • 前置元数据只读 Gamma 认识的键，按行打补丁，未知的键原样保留。
  • 编码、字节顺序标记（BOM）、换行符和末尾换行都属于文件，保持不变。
  • 不是 UTF-8 或超出导入器限制的文件，会成为不能编辑的页面，并注明原因。

链接：远端与本地唯一写法不同的地方

Gamma 中存储[[page id]]，以及上传文件的地址
⇄
本地文件中的写法[[Title]]、[[dir/Title|alias]]、[text](path.md)、![[fig.png|300]]
  • 合并基准按块记住每个链接原来的写法；编辑没动到链接，拉取时就按原样写出。
  • Gamma 的提及没有显示文字，所以别名在 Gamma 里显示为页面标题，在文件里保持不变。
  • 新链接沿用仓库的习惯：仓库有 Obsidian 设置时照它来（wikilink 还是 Markdown 链接，最短路径还是相对路径，附件文件夹）；具体键名要对照真实仓库核实。
  • 重命名一条笔记在 Gamma 里什么都不会断，因为 Gamma 按 ID 链接；其他文件里还是旧名字，Gamma 会提出改写它们并给出数量，与 Obsidian 一样。

拉取与推送，各五步

拉取：Gamma 中的改动 → 本地文件像 git pull：远端的改动打成补丁应用到本地文件；提交后片刻进行
  1. 求差sync_tree.diff(合并基准的树, 页面树) 得出操作。
  2. 把每个操作变成对合并基准文本的一处编辑set 用旧外壳套住新内容替换区段；insert 在前一个兄弟的子树之后加一个区段，外壳仿照最近的兄弟，没有就仿照文件（项目符号、缩进单位）；move 剪切并粘贴子树的区段，按新深度缩进；delete 剪掉区段和一个间隙。
  3. 检查：解析结果还是页面的树吗？解析器或编码器出错，变成一次看得见的等待，绝不变成损坏的文件。什么都不写；页面显示“未写入磁盘”及原因，编辑留在 Gamma 里。
  4. 检查：本地文件还是合并基准那一版吗？先比大小和时间，再比哈希。先把磁盘上的改动推送进来，再从头写。
  5. 原子替换写进目标旁边的临时文件，再重命名覆盖（storage.write_atomic，带 Windows 重试；扫描认得临时文件名并跳过）。被替换的字节进入历史；新的合并基准记下文本、哈希和 stat，扫描认得自己的写入，不会产生回声。
推送：本地文件的改动 → Gamma像 git push：带着合并基准提交，远端做三方合并；扫描发现后进行
  1. 等文件稳定与推送的 PDF 一样。读完再 stat 一次，读的期间变过就等下一次扫描；哈希与合并基准相同，只刷新 stat。
  2. 把新块与合并基准的块配对先按锚点，再按顺序找内容完全相同的块，配对之间剩下的两两视为编辑；其余是插入和删除。
  3. 得出目标树配对上的块，加上页面中没有区段的块（手写、纸张、文本框），后者留在原处。
  4. 三方合并sync_tree.diff(合并基准, 目标) 以客户端 disk 的身份走正常的操作路径，每个 set 带上 base。合并基准之后在 Gamma 里输入的文字会合并进来，打开着的编辑器看到改动像协作者的一样到达。
  5. 更新合并基准文件和得到的树成为新的合并基准。页面若仍与文件不同，接着运行左边的拉取。

冲突：本地文件为准

Markdown 装不下的

  • Gamma 是大纲工具，文件是文档。嵌在非标题块下面的块，在 Markdown 里只能是列表，所以这样的编辑会让两个块在文件里都变成列表项。
  • 顶层的一个块里含空行，再读取时成了两个块。
  • 这两种情况都在一轮之内平息：Gamma 接受文件的形状。手写、纸张和文本框永远不进入 Markdown。

PDF 与批注

PDF 只推送：Gamma 绝不写它没放进去的 PDF。一条高亮在笔记文件里写成带页码的引文，其他工具也能读；矩形区域、手写和文本框留在 Gamma 的数据库。

哪个是这篇论文的笔记文件

  1. 前置元数据以 source 指向这个 PDF 的 .md，不论它在哪里（仓库导入器现在就读这个字段）；
  2. 否则，PDF 旁边与它同名的那个；
  3. 都没有：第一次写入笔记或高亮时创建，放在 PDF 旁边，或仓库设置指定的笔记文件夹。只读过的 PDF 什么都不创建。

写进笔记文件

一条 > [!quote] 标注框：标题链接到 PDF 的那一页，引用的原文，下面是用户自己的批注，以及说明这是哪条高亮的 ^ 锚点。这是其他工具能读的部分：一段带页码的引文，经得起任何变化的锚点。

不写进文件

高亮的矩形区域；Obsidian 的 selection= 数字也不写，它们索引的是某一个渲染器的文本层，已经坏过一次。

---

> 被高亮的那句原文……

我在这条高亮下写的批注。

为什么其余的留在数据库（决定 5）

  • 手写和文本框需要懂它们的合并。Gamma 有：按笔画、按键，在它的操作路径和镜像里。仓库里的旁车文件会把这些数据交给 Dropbox、Syncthing 或 git，它们只保留一个写入者的文件，丢掉另一个的。Zotero 正因为这个拿掉了“把批注存进文件”。
  • 旁车文件每画一笔就要写一次，而且写在用户要求 Gamma 别打扰的目录里。
  • 它会成为数据库之外的第二份事实，还得有自己的同步。
  • 其他工具的用户丢掉的，是按路径索引的数据。这里数据挂在页面上，页面靠文件 ID、哈希和 /ID 跟随文件的移动，靠重新定位跟随新的字节。

代价，以及如何弥补

  • 仓库复制到另一台电脑，带过去的是笔记和每条高亮的引文与页码，不包括手写和精确的矩形区域；重新定位引擎会按文字把高亮重新放上去，作为需要确认的粗略匹配。
  • Gamma 的备份包含页面，因而包含批注，但从不包含仓库的文件，那些由用户自己备份。
  • 要把批注交给别的阅读器，仍然用导出带批注的 PDF，要求时才写。

原文 · Rules that keep files safe

保护文件的八条规则

合起来是一句话：本地文件只为你在 Gamma 中做的事而写，写前核对，删除只进回收站；目录不见了当作离线，扫描才是事实。

  1. 只写标记，先说再写建立目录仓库只写 .gamma/，别无其他，并事先说明，不论它往哪个方向同步；单文件仓库和阅读器什么都不写。
  2. 只因 Gamma 中的操作而写对该页面的编辑、重命名、归入，或事先说明要写什么的命令（改写链接，附数量）。笔记以补丁写入：重新解析核对、对照当前文件核对、用重命名放到位；被替换的内容保留若干天。
  3. 进回收站，三十天内不删文件移到 .gamma/trash/，不满三十天绝不删除；磁盘上删除的文件，让它的页面进入「最近删除」。
  4. 不懂的不碰点开头的目录、node_modules 和仓库的忽略列表不读；Windows 拒绝的名字、只差大小写的两个名字，报告而不改名。
  5. 冲突时保留文件并记录 Gamma 一方。
  6. 根目录不见了是离线，不是空了没有标记或标记属于另一个仓库，仓库就停止；一轮要移除很大比例的页面或文件时，暂停并询问（rclone、Unison 也这样）。单文件仓库的文件不见了，就是「缺失」，页面留下。
  7. 路径只由选择器给出Gamma 的网页从不指定路径，由系统原生对话框指定，与今天一样。只有桌面应用自己的服务器绑定仓库、读取关联文件（GAMMA_FOLDER_LINKS 规则）；不碰数据目录里的任何东西，不跟随指向根目录之外的符号链接。
  8. 扫描才是事实，监视器只是提示每个文件一次 stat 就能发现变化（推送 PDF 的循环已经这样做）：仓库有页面在窗口里打开时每隔几秒一次，窗口获得焦点时立刻一次，其余时候随 30 秒的定时轮询。原生监视器只把下一次扫描提前，漏掉一个事件只损失几秒。

分层与构建顺序

先做只读的部分：接缝、阅读器和新用语、只推送的仓库。往返校验通过后，第 3 步才开启补丁式拉取，让 Gamma 写你的笔记文件，并加上「编辑文件」；第 4 步把今天的仓库放到同样的行上，第 5 步让 NAS 上的文件夹推送全部内容。

三层：每层单独有用，每层在下一层之前构建并测试

L2目录绑定：一个被扫描的根目录。路径即身份，目录即文件夹，跟踪重命名和删除。使用者：目录仓库
L1笔记双向：页面的块树通过补丁与一个 .md 保持一致。使用者：推送笔记的仓库；以后是只拉取的仓库的笔记文件
L0关联文件（linked file）：页面的 PDF（或笔记中的图片）的字节留在这台电脑的某个路径上，Gamma 只读不写。使用者：阅读器、单文件仓库、目录仓库

L0 的改动属于 storage：已存的 PDF 以哈希命名，下游一切都按这个名字索引（查看器的清单和缓存、文本索引、AI 的阅读、高亮的 pdf_position.doc_id）。一个命名上传的字节也可以位于数据目录外一个记录下来的路径，附带哈希时的大小和时间。读取先查 stat；文件变了就重新哈希，新哈希就是今天「跟随文件」所做的替换，连同重新定位。列出上传目录的东西永远看不到关联文件，这正是想要的：不计配额、不被清除、不进备份或异地拷贝。含关联页面的工作区备份里有它们的笔记和批注，没有它们的文件。

构建顺序

  1. 接缝（seam）自己拼上传路径的读取方改走 storage：导出（routers/export.py）、ink_view、ops、镜像（sync_engine）、zotero_local 和一处导入。行为不变；不管之后做什么，这一步都值得做。
  2. 阅读器与用语L0、「已打开的文件」、「添加到文库…」、「打开方式」的改变及其偏好设置。两个菜单项、面板和指南换上“界面用语”里的词，让改名一次落定，赶在任何新东西建到它下面之前。
  3. 只推送的仓库标记、附摘要的扫描、经新解析器由 .md 生成的页面、原地读取的 PDF、磁盘上的改动实时到达。仓库页面的笔记暂不能在 Gamma 中编辑；高亮和聊天可用并留在 Gamma。往返校验对每个文件运行并报告。
  4. 笔记双向补丁写入器（拉取）、历史、冲突；从 Gamma 创建、重命名、移动文件和把文件移进回收站；高亮写成标注框；改写链接的提议；「编辑文件」。以第 2 步的往返校验为门槛
  5. 今天的仓库放到同样的行上只拉取的仓库的笔记由编码器写出，状态移出目录，并可开启推送：笔记，以及放进去的 PDF 成为页面（disk-to-gamma.md 的第 3 步）。
  6. NAS 文件夹推送全部内容通过 HTTP。

现有功能的去向

「保存到这台电脑」的文件夹保持承诺和位置：把文库放到磁盘上给智能体和其他应用使用，NAS 的文库也一样。成为只拉取的同步仓库，推送照原来的箭头，关或仅 PDF；folder_links 的行保留，kind 读作范围；升级后的第一轮在文件旁写入 .gamma/，并在面板里说明。本地服务器上的仓库之后可以开启全部推送，智能体对笔记文件的编辑由此进入 Gamma。
「跟随」的文件成为单文件仓库，也就是最小单元：手稿的构建结果由它送到他人评论的页面。磁盘上对它们什么都不变。
两个名字去掉：两个菜单项、面板的用词、指南的两节（见“界面用语”）。gamma_sync.py 保留它的命令，增加 pull。
「打开方式」变成阅读器。
NAS仓库的一轮同步按今天那一轮的源与汇来写，所以 NAS 上的文件夹以后也能推送：通过 HTTP 和写令牌推送，PDF 存在 NAS 上，因为 NAS 读不到这块磁盘。这是计划中通往 iPad 的路；副本里改为存入 PDF 的仓库是另一种可能，见“待定”。
LaTeX作为仓库打开的项目目录，会把 build/main.pdf 显示为一个随每次编译更新的页面，高亮随之移动。.tex 文件作为文件支撑的块是最简单的透镜（内容就是文件）；在桌面上，项目编译不需要物化的拷贝。

待定与不做

七个问题仍未决定；六种做法明确不提议，大多是把 Gamma 的数据写进本地目录或你的文件。

待定

  • 「已打开的文件」做成内含页面的页面，还是用它自己的标记。
  • 一轮同步可以移除多大比例的页面或文件，超过就询问。
  • 回收站用 .gamma/trash/，还是系统回收站（服务器不加依赖就够不着）。
  • 仓库里的页面里的页面：只在前置元数据写有 parent: 时成立，与今天「保存到这台电脑」的写法一样。
  • 既不是笔记、不是 PDF、也不是笔记里显示的图片的文件：起初不列出。
  • 提及是否要有显示文字，好让别名在 Gamma 里也显示。
  • 副本里的仓库是否改为存入 PDF 而不是原地读取，好让副本把它带到 NAS。

明确不提议

  • 仓库里放数据库，理由与 Zotero 给出的一样。
  • 普通文件夹以文件为准。它们保持原样，协作、副本和 iPad 都依赖这一点。
  • 建立关联时往用户的文件里加 ID、前置元数据或重新排版。
  • 把批注写进用户的 PDF，除非是明说如此的导出。
  • 仓库里的批注文件。若有一天必须在两台之间没有 Gamma 服务器的电脑上携带手写，形状已经清楚：每个 PDF 一个文件，以其哈希为键，像 Sioyek 和 KOReader 那样。
  • 关联了 Zotero 的工作区里的仓库；以及副本里仍原地读取 PDF 的仓库（见“待定”）。
