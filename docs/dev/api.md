# API reference

All endpoints are same-origin under `/api`. The frontend never talks anywhere
else; in dev, Vite proxies `/api` → `127.0.0.1:9001`.

## Auth model

- A `session` cookie identifies the user (middleware sets
  `request.state.user_id`, the account's id, and `request.state.user`, its
  username). Account-level endpoints use `require_user_id` (or
  `require_user` for the username), which refuses an integration token
  ("Integrations" below). The API names people by username in both
  directions; the account ids storage keys on never need to reach a
  client ([user_db.md](user_db.md) "Accounts are named by id"). Where one
  does appear — the `actor` of an op-log batch or of a change-feed
  `deleted[]` entry, a job's `owner` — it is an opaque string a client may
  compare but never shows; no client reads them today.
- Every data endpoint works in a **workspace** ([workspaces.md](workspaces.md)):
  `?ws=` or the `X-Gamma-Workspace` header names it, nothing means the
  account's default personal workspace. `require_ws(request)` admits any member
  or signed-in non-guest account allowed by public workspace access,
  `require_ws(request, write=True)` editors and owners (a viewer gets 403);
  a caller without effective access gets 403. The returned workspace id is what the data helpers
  take; the account's id (`auth.actor_of`) is the actor.
- Share tokens (`?share=<token>`) are the ONLY unauthenticated **read** path.
  A token is `<workspace id>.<secret>`, split at the first dot (a workspace
  id never holds one; `db.share_token_workspace` is the one parser), so a
  router can place share traffic by the prefix without a lookup. It is
  stored whole in `shares.token`, and every lookup is by the whole token.
  `resolve_ws` returns the session's workspace, or the workspace of the share
  named by a valid `?share=` token. There is no `?user=` fallback: it would
  trust any username and leak whole accounts. A share names a PAGE of a
  workspace (its root block, so note pages share exactly like papers; the
  PDF is the page's `doc` property) with the pages inside it, read
  live ([home_library.md](home_library.md#sub-pages)), or a FOLDER (a
  folder block's id: the pages filed there or below it with the pages
  inside them, read live, so pages filed later join, pages moved out leave
  and a folder moved in brings its pages). `auth.share_scope()` hands every
  share-enabled endpoint a `ShareScope`, and the endpoint asks it what is in
  reach (`allows_page`, `allows_block`, `allows_folder`, `lists_library`,
  `pages` and `block_ids` for a read that scans the workspace;
  `blocks_store.assert_block_in_scope()` for block reads) instead of
  branching on the share's kind. A token reaches only its own pages'
  subtrees and assets: the files their documents name (`doc.hash` +
  `doc.ext`: a stored PDF, an address's cached copy, the file a duplicated
  page shows), the uploads their blocks reference (found
  by walking the shared pages' subtrees, never the workspace; a yes is
  remembered for `uploads.SHARE_READ_TTL_S`, 5 min), the files an edit
  share's visitor stores through `POST /upload-image` or
  `POST /upload-file` (`uploads._share_reads_own_upload` remembers that
  yes as the file is stored, so a picture dropped on a shared page shows
  before a saved block names it; the visitor sent those bytes), the
  address their own `doc.url` names through the proxy. Backlinks and other pages are refused
  (403). The root listing and folder export are refused for a page share;
  a folder share gets the pages in reach and exports its folder or a
  subfolder.
- Share reads are readable **cross-origin**: a GET carrying `?share=` or
  resolving `/share/{token}` answers `Access-Control-Allow-Origin: *`
  (`auth._apply_share_cors`), refusals included, so another Gamma's
  frontend can pull a shared page or folder into its own library
  browser-side (a share link pasted into the "+" box, the share view's "Add
  to my library" — [import_export.md](import_export.md)). A `mode=gamma`
  export through a token carries only what the share shows: a folder export
  the exported folder (the shared one, or a subfolder the link names) at the
  top level with no folder above or beside it, a page opened through a
  folder share its folders up to the shared folder, a page share no folder
  or label; and of the chats only the pages' active ones
  ([import_export.md](import_export.md#gamma-to-gamma-export)). Every format
  through a token keeps to the share: a `[[ref]]` or `![[embed]]` of a block
  outside it stays as typed and an upload it cannot read stays out of the zip,
  as `/blocks` and `/uploads` refuse them. `*` makes browsers drop credentials,
  so a cross-origin fetch is a stranger's: only `anyone` links open that way.
  Writes and every other endpoint keep the same-origin default.
- **Share permissions** (`shares.audience` / `role`, the invited people in
  `share_users`, `auth.share_access`) are Notion-shaped and additive:
  members of the page's workspace keep their workspace role (editors/owners
  edit, viewers view); the sharer INVITES people (`users: [{name, role}]`
  by username, stored as `share_users` rows by account id — a deleted
  account's go with it) who get in with their own `view`/`edit` whatever
  general access says — on a server with Gamma Cloud sign-in also people
  without an account here yet: named by their e-mail address, whose
  invitation (`email_invites`, `gamma/email_invites.py`) the account
  server mails and which waits until a cloud sign-in through its mailed
  link, and only that, makes it a `share_users` row; or named by
  their Gamma Cloud username, whose invitation waits
  (`pending_share_users`, `gamma/shares.py`) until their first cloud
  sign-in does the same; everyone else goes
  through general access —
  `audience` `anyone` (no session needed, with the share's `role`), `users`
  (any signed-in non-guest account, with the share's `role`), `list` (nobody
  beyond the invited). When a request carries `?share=`, the token decides
  WHICH WORKSPACE is read (the share's — a signed-in visitor sees the shared
  page or folder, not their own library) while the session decides whether the
  audience gate admits them; a refused token is 401 when signing in could
  help, else 403. `edit` shares let `require_ws_writer` resolve the
  workspace for the block writers — `POST /blocks`, `PUT /blocks/{id}`,
  `DELETE /blocks/{id}`, `PUT /blocks/{id}/children`, `POST /blocks/{id}/reorder`,
  `POST /pages/{id}/ops` (and the page websocket, view or edit),
  `POST /upload-image`, `POST /upload-file` — each of which confines the touched blocks to the
  shared pages (no new pages, no deleting/moving a page itself, no changes to
  a page root's properties — so a folder edit share can never re-file pages
  into or out of its folder). Comment writes take `auth.require_commenter`
  instead: any member (viewers too) and any signed-in account a share
  admits, view or edit, confined to the shared pages; never a link visitor
  or a read-scope token, and a feedback-scope token for a reply or a
  resolve on a work folder's file only ([comments.md](comments.md) "Who may
  comment"). A
  share visitor therefore sees the usernames of the people who wrote or
  resolved comments on the shared page, as presence shows them. Everything
  else stays session-only.
- **Link visitors.** An `anyone` + `edit` share makes the link itself the
  key: whoever opens it edits the page, without an account. Such a writer
  (no session, or a guest account — `auth.is_link_visitor`) is recorded
  as `link:<name>` (`auth.actor_of`): the display name the share view keeps
  per browser (`src/collaboration/linkName.js`, generated "Curious Otter"
  style, renamable from the topbar tag), sent percent-encoded as the
  `X-Gamma-Name` header on every API call (`utils.js` injects it) and as
  `?name=` on the page websocket; cleaned server-side (`auth.link_name`:
  control characters out, 40 chars, `Anonymous` when empty). A label, not
  an identity — the log names an account by its id, never `link:…`, so it
  never confuses the two. Link visitors alone are rate limited per IP (`auth.link_ratelimit`:
  `collab.LINK_OPS_PER_MINUTE` op batches, `uploads.LINK_UPLOADS_PER_5_MIN`
  uploads); their uploads count against the page's workspace like any
  share editor's. Flipping the share back to `view`, or stopping it,
  revokes the link's writes at once (the grant is re-read per request, and
  open page sockets are re-checked by `collab.revalidate`).
- **Unknown tokens.** A `?share=` that names no share is counted per IP
  (`auth.note_share_miss`, from `share_grant`, `GET /share/{token}` and the
  page socket): past `auth.SHARE_MISSES_PER_5_MIN` (30) in five minutes the
  address gets 429 for the rest of the window and the server log carries
  one warning per window — the admin's only signal that someone is probing
  for links. A token without the `<workspace id>.<secret>` shape, or whose
  prefix is not its share's workspace, is unknown too (`auth.share_lookup`
  refuses it). So is every link minted before schema version 32, whose
  token is the bare secret: step `share_token_workspace` rewrote the
  stored tokens, and the Share popover shows the new link
  ([migrations.md](migrations.md)). The secret is 96 random bits, so
  guessing one is hopeless (the workspace prefix is no secret). The
  throttle is about noise and visibility, not about protecting the
  space.
  The link-visitor throttles above log the same way.
  Keep that read/write + scope distinction when adding endpoints.
- Outbound fetches of user-supplied URLs (PDF proxy/resolver, AI PDF
  re-download) go through `gamma.net_guard.guarded_urlopen`, which blocks
  non-http(s) schemes (`file:`, `ftp:`, …) and hosts that resolve to
  loopback/private/link-local/metadata/shared-address-space addresses (SSRF),
  re-checking on every redirect. Its HTTP(S) transport validates the complete
  DNS answer and connects directly to a validated numeric address, closing
  the DNS-rebinding gap between a URL check and a second resolution. HTTP
  Host and TLS certificate/SNI checks retain the original hostname. Guarded
  fetches take the server's network route ([network_proxy.md](network_proxy.md)):
  the admin's proxy and bypass list, never a proxy a member chooses.
  Through a proxy they stay pinned: the host is resolved and the whole
  answer checked here, and the proxy is asked for the checked address
  over a tunnel (CONNECT or SOCKS5 to it, an http URL's too), the hostname
  kept for Host and TLS. Only the admin's "Let the proxy look up names"
  (`proxy_dns`) asks the proxy for the name, after checks by form (an
  address written as a name, `127.1` or `10.0.0.5.`, still counts as one)
  and a local lookup that refuses private answers outside the fake-IP
  ranges 198.18.0.0/15 and fc00::/18; the proxy then decides which
  addresses such a fetch reaches.
- Outbound HTTPS is urllib's default context, verified against the CAs
  OpenSSL was built to find; outside Windows Python reads no system trust
  store, so the macOS Keychain never counts. Where those paths hold
  nothing, such as the desktop app's frozen server on a Mac without
  python.org's Python, `create_app` points `SSL_CERT_FILE` at certifi's
  bundle (`app._verify_https_with_certifi_when_no_cas`); otherwise every
  call (the AI, the ChatGPT sign-in, Gamma Cloud) fails with
  `CERTIFICATE_VERIFY_FAILED`. A proxy that re-signs HTTPS with a root
  that is only in the Keychain still fails: give the server that root
  with `SSL_CERT_FILE`.
- Workspace ids and doc ids are validated (`db.safe_ws_id` / `db.safe_doc_id`,
  used by `ws_db_path` / `ws_uploads_dir`) before they
  become filesystem paths — no traversal.
- The session cookie is `HttpOnly; SameSite=Lax`, and `Secure` when the request
  is HTTPS (auto via scheme / `X-Forwarded-Proto` — off on plain-HTTP LAN so
  login still works there). Sessions are enforced server-side against
  `SESSION_MAX_AGE` (expired rows are deleted in the middleware) and are revoked
  when the account's password is changed.
- A cloud identity (Sign in with Gamma Cloud, [cloud_accounts.md](cloud_accounts.md))
  ends in the same `sessions` row as a password login: the callback mints it,
  nothing downstream can tell the difference. The row is marked
  `via = 'cloud'` so the hourly grant check can end it when the account
  server revokes the grant.
- `/api/login` and `/api/login-guest` are rate-limited per IP/username
  (`gamma/ratelimit.py`, in-process fixed windows → 429; a guest login 10
  per IP per hour), as are share-link
  visitors' writes and unknown share tokens (above; those log a warning
  once per window through `check`'s `on_first_exceed`). Not an edge WAF; add
  one for large public deployments. "Per IP" is the connection's peer
  address (`ratelimit.client_ip`); `X-Forwarded-For` counts only when
  uvicorn itself rewrote the peer from it, which it does for the proxies
  `FORWARDED_ALLOW_IPS` lists (127.0.0.1 by default, the Docker image
  too: a deployment behind a proxy must name the proxy, or its compose
  network's pinned subnet — `cloud/deploy/` does for the demo and the share
  host — else every visitor shares the proxy's bucket). The counters are bounded
  (`ratelimit.MAX_KEYS`): expired windows are swept when the table fills,
  then the oldest.
- JSON answers of 1 KB or more are gzipped for clients that accept it
  (`gamma/compression.py`, level 3: a 5,000-block subtree goes from 2.1 MB
  to 0.47 MB for about 22 ms of compression, done in a worker thread above
  256 KB). Only a whole `application/json` 200 of known length is
  touched: streams (the AI chat and translation NDJSON, event streams),
  files and their range requests (uploads, PDFs, the app's assets) and
  anything already encoded pass through as they are. A dict a sync
  endpoint returns is encoded on the event loop, so the reads whose answer
  can be large — the tree reads (`GET /blocks/{id}/subtree`,
  `/blocks/{id}/children`, the library listing), a block search, the two
  searches, a conversation (`GET /chats/{bucket}`), the op-log catch-up
  (`GET /pages/{id}/ops`) and the covers (`GET /page-snaps`) — answer a
  `json_response.OrjsonResponse` they encoded in their worker thread (a 5,000-block page stalled
  the loop ~175 ms otherwise). It encodes with
  orjson, in about a tenth of the standard library's time, and
  `blocks_store.load_json` parses each row's `properties` with it in about
  a fifth. A page's subtree is read by its `page_id` (one indexed read;
  every block of a page carries its id) rather than the recursive walk
  down the parents, and `kind` is computed in Python from the parsed
  properties (`blocks_store.block_kind`, the generated column's rule)
  instead of being selected: the column costs up to six JSON functions per
  row. On an in-memory database, 5,000 highlight-like blocks of 1.3 KB
  each: 42 ms the old way, 8 ms this way. A stored NaN goes out as null and a stored lone surrogate as
  U+FFFD (both were a 500; a write refuses a new NaN, [collab.md](collab.md)
  "Ops"); what orjson refuses, such as nesting past 255
  levels (a tree about 125 blocks deep), falls back to the standard
  library. Writes keep `json.dumps`, so the stored text does not change.
- Every response carries baseline hardening headers (`X-Content-Type-Options`,
  `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, `Content-Security-Policy:
  frame-ancestors 'self'`, and HSTS on HTTPS). SVG uploads are served
  `Content-Disposition: attachment` + `CSP: default-src 'none'; style-src
  'unsafe-inline'; sandbox` so they can't run inline as stored XSS
  ([pictures.md](pictures.md#svg-pictures)).
- The Zotero sign-in's callback, a fetch handoff's `/go` and the ChatGPT
  sign-in's listener on localhost:1455 answer with the small page of
  `html_page.py`. It carries `no-store` and a CSP under which it loads
  nothing and is framed nowhere.
- `/api/admin/*` additionally requires the `is_admin` flag.
- A hosted container whose plan made it read-only answers every POST, PUT,
  PATCH and DELETE under `/api/` with 423 `{detail, read_only: true}`,
  except sign-in and sign-out, the export jobs, marking notices seen, the
  Inbox's marks (`/inbox/…`) and `/admin/hosted/sync` (`hosted.READ_ONLY_ALLOWED`,
  [cloud_accounts.md](cloud_accounts.md) "Hosted containers"). The reads
  sent as a POST, because their ids do not fit a URL (`/pages/by-docs`,
  `/pages/summaries`, `POST /block-search` and `POST /document-search`:
  `hosted.POST_READS`), are
  reads there: they pass and move no last write.
- A workspace a delete holds (its job running, the final copy being
  written, until it is stopped or the workspace is gone) takes no more
  changes: every write the workspace gates refuse (`require_ws(write=True)`,
  `require_ws_writer` with an edit share, `require_commenter`, a restore or
  a merge into it) answers 423 `{detail, error: "workspace_deleting",
  workspace}` with the header `X-Gamma-Workspace-Deleting: <id>`, and
  `/session` lists the workspace with `deleting: true`. Reads, exports,
  the delete's own Stop and a person's own preferences go on
  ([workspaces.md](workspaces.md) "Deleting a workspace").

### Workspaces (`workspaces.py`) — see [workspaces.md](workspaces.md)
| Method | Path | Purpose |

Route order matters: the static-prefix routes (`by-doc`, `children`,
`subtree`) must stay registered before `/blocks/{block_id}`.

**The block dict** (`blocks_store.block_to_dict`, what every block read
answers and every subtree node carries): `{id, parent_id, position, content,
properties, created_at, updated_at, page_id, kind}`. `page_id` and `kind`
are read-only, derived by the server, never taken from a write: `page_id` is
the page the block lives in (its own id on a page; `folders` / `labels` in
the trees), `kind` one of `page`, `folder`, `label`, `ink`, `text_box`,
`picture`, `sheet`, `recording`, `link`, `highlight`, `note`
([user_db.md](user_db.md) "pages.db"), the order the server tests them
in; `highlight` is a block with a `pdf_position`, an `image_position` (a
region of a picture) or a `text_position` object, so a reader of the PDF's
shape tests `highlights.is_highlight`, never the kind alone. A block's
document, when it has one (a page's PDF, picture or file), is its
`properties.doc` ("A page's document" below). `POST /blocks` answers the block as
stored (it reads it back). The Properties popover
([ui-design.md](ui-design.md#the-properties-popover)) reads
`GET /blocks/{id}` and names the block by this `kind` while the server's
properties match the tab's; otherwise by the client's own predicates.

**The highlight shape** (`gamma/highlights.py`, the frontend's
`shared/model/blockModel.js`). A block placed on a PDF page by rectangles
— a highlight, a link region, an ink group — carries
`properties.pdf_position`: `{pageNumber, width, height, boundingRect: {x1,
y1, x2, y2}, rects: [{x1, y1, x2, y2}, …]}`, the 1-based page, the page as
it was measured when the place was taken (the viewer's page at its zoom
then, an ink file's page in points, an imported annotation's page box) and
the rectangles in that frame, top-left origin, `boundingRect` their union;
`area: true` on an area highlight. A text highlight may also carry
`properties.style`, how it marks its passage: `underline`, `squiggly` (a
wavy underline) or `strikeout`, drawn as a line in its colour's line tone
(`colors.line_color`, the frontend's `lineColor`) and written to the
annotated PDF as the markup of that name; no `style` is the wash, and an
area never has one (`shared/model/markStyle.js`). Changing it keeps the
block, its notes and its place. After the page's PDF is replaced
([highlight_relocation.md](highlight_relocation.md)) a highlight's
position may also carry `doc_id`, the stored file (a page's `doc.hash`,
the content hash; a duplicated page's is the file it shows; `unstored` for
a page that showed its file from another URL alone) its rectangles were
measured on, written by the replacement when
that is no longer the page's PDF; a position without it was measured on the
page's current PDF, which is what the viewer, the imports and a move by
hand write. `lost: true` marks one whose text the run did not find in the
new file (drawn hollow where it was; it keeps its `doc_id`, the file its
rectangles are from). `approx: true`
marks one drawn dashed, pending until the person accepts it or moves it:
placed where its text was found roughly, with `match`, how alike the two
read (0 to 1, two decimals, at most 0.99), or, without `match`, an area
placed by estimate or one measured on another file that nothing placed
(left where it was; it keeps its `doc_id` until accepted). A later run
also places one solid: its text found exactly, or an area's confirmed file
put back. Beside them `prev` keeps where
it was before the run that first drew it dashed, for the review card:
`{doc_id, pageNumber, rects: [[x1, y1, x2, y2], …], quote}`, the file its
rectangles were measured on (also one no longer stored), its page there,
its rectangles as fractions of that page as shown (top-left origin, four
decimals, at most 200) and its quote before the run respelled it (`""` for
an area, at most 1000 characters). Accepting it (the web app's Accept)
drops `approx`, `match`, `prev` and `doc_id` and keeps the rectangles,
now the page's current PDF's. A lost text highlight may also carry
`closest`, the best place the run found for its text in the page's current
PDF that read too unlike it to be applied (under the account's threshold,
at least half alike): `{pageNumber, width, height, boundingRect, rects,
match, quote}`, a place in this same shape (at most 200 rects), how alike
it read (two decimals, at most 0.99) and its text as that file spells it
(at most 1000 characters); the web app's review card offers it, and its
Use closest match writes that place and quote, without `lost`, `closest`,
`doc_id` or the rest. A move by hand writes a position without any of
these; a run writes a placed one without `doc_id`, `lost` and `closest`,
replaces or removes a lost one's `closest` by what it found, matches a
pending one from its `prev` (its reference: the last place someone
confirmed), placing it dashed again with that `prev` and a `match` against
it, solid without `approx`, `match` or `prev` when found exactly, or lost
at `prev`'s place (its page, rectangles, `doc_id` and quote, `prev` gone),
and writes one it places solid without `approx`, `match` or `prev`
([highlight_relocation.md](highlight_relocation.md#the-reference)); a
replacement of the PDF drops every `closest`, a place in the outgoing file.
A backup's restore keeps them all (`prev` and `closest` only in their own
form). A reader
scales a rectangle by its own page size over `width` / `height`. A highlight whose place on its page is
not known (a Logseq import without positions) has `pdf_position:
{pageNumber}` alone. The block id is the highlight's id: a link region
names a highlight on the page it links to by `link_block_id` (beside
`link_url` / `link_page_id`), and a highlight placed by its page alone
names the one on the PDF it was attached to in the notes (attach mode) by
`linked_highlight_id` (a block id, taking that one's page). A text box and a
picture have no position; the page of each is `pdf_page`
([text_boxes.md](text_boxes.md), [pictures.md](pictures.md)). A highlight's `properties.color` is
its concrete colour as `#rrggbbaa` — a palette swatch at the highlight
alpha (0.65) when made in the viewer, an annotation's own `/C` and
`/GammaAlpha`, else `/CA`, when imported from a PDF — never a palette slot, so every member of a
workspace and every export sees the same colour whatever palette their
account keeps ([settings.md](settings.md) "Colors"). `gamma/colors.py`
(the frontend's `shared/model/palette.js`, both held to
`tests/shared/colors.json`) reads the older `rgba(…)`
and `#rrggbb` spellings too, which an older server or export can still
send; workspace step 37 respells stored ones. **A region of a picture** (a
page whose document is an image) is the same block with
`properties.image_position` in place of `pdf_position`: `{width, height,
boundingRect: {x1, y1, x2, y2}, rects: [{x1, y1, x2, y2}], hash}`, the
frame the picture's own pixels as drawn (its natural size, EXIF
orientation applied), one rectangle equal to `boundingRect`, whole pixels,
and `hash` the stored file's stem of the version it was drawn on, always
written: "drawn on another version" is read, never stamped (`hash` differs
from the page's `file_hash`), so a replacement writes no op on regions,
and `hash` holds no file (the version a thread needs is held by its
anchor, [feedback.md](feedback.md)). No `pageNumber`, no `area`, no
`style`: every region is a box, and readers scale by fractions
(`highlights.region_box`, the client's `regionBox`), so a figure rebuilt at
another size keeps the region's relative place. Regions are never
relocated and are no Zotero annotation; the exports write one as a note.
`highlights.is_region` is their test, the twin of `is_highlight`
(`shared/model/blockModel.js` `isRegionBlock`, `isPlaceBlock` for either,
`positionKeyOf(doc)` the key a page's document stores its places under).
**A range of a text file** (a page whose document is `format: "text"`: a
source file, a log) is the same block with `properties.text_position`:
`{line, col, end, end_col, prefix, suffix, hash}`. `line` and `end` are
its first and last line (1-based, `end` inclusive, the words a feedback
entry's `source` uses), `col` and `end_col` columns in them, 0-based and
counted in code points of the decoded line (the line break not counted;
the client converts CodeMirror's UTF-16 columns), `end_col` exclusive. The
block's `quote` is the selected text verbatim, its lines joined with `\n`,
at most 10,000 code points, and never ends in a line break: a selection
that ends at column 0 of a later line ends at the end of the line before.
`prefix` and `suffix` are the 40 code points of the file just before and
just after the quote (line breaks kept, shorter at the file's ends), and
`hash` the stored stem of the version it was measured on, always written,
as a region's is: "measured on another version" is read, a replacement
stamps nothing on a range, and `hash` holds no file. The range carries its
own context, so when the file changes the run that finds it again reads
the new version alone (`gamma/documents/text_anchors.py`,
[highlight_relocation.md](highlight_relocation.md)). It writes the PDF's
words beside the place: `lost: true`, `approx: true` with `match`, `prev:
{hash, line, col, end, end_col, quote}` (where it was before the run that
first drew it dashed, its quote whole: a later run matches the range by it,
and one lost goes back to that span) and a lost one's `closest: {line, col,
end, end_col, match, quote, hash}` (its best place under the threshold in
the version `hash` names); both quotes at most 10,000 code points, a
range's own cap, not a PDF's 1000. Readers never trust the columns alone:
the quote at `line`..`end` decides, a column past its line is clamped, and
a start at its line's end moves to the next line's start, as an end at
column 0 moves back (`clamp_span`); a whole number may be written `3.0`, as
a browser reads it. Nothing validates the shape on write, and a malformed
one (`highlights.text_span` answers None) is read as a note; the run reads
what it stores as a selection writes it (a quote of at most 10,000 code
points, a prefix and suffix of 40). A range may have
a line `style`, never an `area`. `highlights.is_text_range` is its test
(the client's `isTextRangeBlock`); `highlights.span_text` cuts a span's
quote and context from the lines, and the client's `contextOf` cuts the
same, both held to `tests/shared/textposition.json`.
Tests: `tests/test_highlight_shape.py` (the shape, its writers, the derived
URL, the text range's helpers), `test_text_anchors.py` (a range found again
after its file changes), `test_block_columns.py` (the kinds, `tests/shared/blockkind.json`), `test_migrations.py` and
`test_restore_consistency.py` (step 30 and an older backup),
`test_colors.py` (the colour spellings, the Logseq names, step 37), the browser
suite's `pdf.mjs` (a highlight made from a selection, its stored colour,
a changed palette swatch, a link region landing on its block).

**A page's document** is one property, `doc`: `{format, name, hash, ext,
at, url?, size?, copy?}` in that order (`gamma/documents/model.py`, the
frontend's `documents/pageDocument.js`, both held to
`tests/shared/document.json`; [documents.md](documents.md) has the rules
and which reader asks what). `format` is `pdf` for every document so far;
`name` the file's shown name (`""` for a clip or a URL page); `hash` the
stem its file is, or would be, stored under, so the stored name is
`hash + ext` (`/api/uploads/<hash><ext>`, which `page_document` and
`pageDocument` derive); `at` where its bytes are read from: `store` (the
workspace's uploads), `path` (a file on this computer,
[synced_vaults.md](synced_vaults.md#a-file-read-where-it-is)) or `url`, the
only one with a `url` (the address it is shown from; the proxy's cached
copy, if any, is stored under the address's hash). `copy: true` marks a
page that shows a stored file it does not own (a duplicated page): no
lookup of the page of a PDF finds it. A nested block may carry a `doc` of
the same shape. Every writer goes through `documents.model.document` /
`check_document`: the stored file's own address given as an address is no
address (`at: "store"`), and without a hash the address of a stored PDF is
a copy of it. The keys a document was kept in before (`doc_id`,
`source_url`, `linked_file`) are no block property: a write that carries
one with a value is a 400 (`PUT /blocks/{id}`, each patch of
`POST /blocks/bulk`, the op path, `POST /blocks`, `PUT /blocks/{id}/children`,
`POST /pages`), one that removes it (`null`) is passed by, and a `doc`
that does not check is a 400 too; a page writer inside the server
(`blocks_store.page_root_props`) drops them. The request bodies keep their
own words (`doc_id`, `source_url`, `original_filename` of `by-doc`, the
attachment and the clip). `original_filename` stays only on a page made
from a Markdown file, the name of that file beside `markdown_import`.
Migration steps 30 and 52 convert older data
([migrations.md](migrations.md)). Tests: `tests/test_documents.py`,
`test_shared_fixtures.py` (the fixture), `test_pages.py` (the attachment
routes and `POST /pages`).

**The library listing** (`GET /blocks/root/children`, `routers/blocks.page_summary`)
carries only what the home view reads — the cards, the folder and label
filters, quick open, the chat and link pickers, the DOI / arXiv matching of
an opened link — one summary per page, in library order: `{id, content,
position, created_at, updated_at, preview, parent, properties}`. Its pages
are those the library lists and the pinned ones (`work_folders.library.SQL_IN_LISTING`,
read by the partial index `idx_ub_listing`): a work folder's file only when
it is in the library or pinned, the client telling a pinned file by its
properties, and a sub-page only when the page it is inside is carried
([work_folders.md](work_folders.md) "The library rule"). A work folder's
directory is read page by page instead (`GET /folders/{id}/pages`), and a
page the listing leaves out by its id (`POST /pages/summaries`). `parent` is
the page's effective parent, `""` for a library page (`blocks_store.page_parents`,
one read per listing): the listing carries sub-pages too, and the home view
leaves them out ([home_library.md](home_library.md#sub-pages)). `properties` holds
those of `doc` (the page's document whole, above: its format and name for
the cards, its address for the link matching, `at: "path"` when its PDF is
read where it is on this computer), `folders`, `labels`
(lists of folder and label ids), `pinned`, `seeded`, `opened_files` (it is the page *Opened files* that holds
PDFs read in place; both [synced_vaults.md](synced_vaults.md#a-file-read-where-it-is),
read by the page menus) and a work folder's stamps `work_folder`, `library`
and `file_name` ([work_folders.md](work_folders.md) "The stamps") the page
has, and `meta` with those of its `title`,
`authors`, `year`, `venue`, `volume`, `doi` and `arxiv_id` it has
(`SUMMARY_PROPS` / `SUMMARY_META`); everything else — `bibtex`, `ppt_cite`,
`summary`, `auto_title`, the rest of `meta`, … — comes with the page itself
(`GET /blocks/{id}` or its subtree). `preview` is the first ~240 chars of the
page's first few child blocks that are no highlight, joined with ` · ` (one
`idx_ub_parent` seek per listed page, so the cost follows the pages, not the
blocks; `""` when there are none). A sub-page has one too: its card in the
pinned and recents strips or a label view shows it.
Beside `children` the listing carries the two trees and the work folders'
counts, read in the same snapshot:

```
{"children": [<page summary>, …],
 "folders": {"seq": 12, "children": [<folder node>, …]},
 "labels":  {"seq": 3,  "children": [<label node>, …]},
 "work_counts": {"<folder id>": 4, …},
 "work_changes": {"seq": 812, "since": 312, "dirs": {"<folder id>": 805, …}}}
```

A node is a block dict (`kind` `folder` / `label`, `content` the name,
`properties` with `pinned` when pinned, and on a work folder's root the
mark `vault: {pull, library}`) plus `children`, its subfolders in
order (`[]` for a label). `work_counts` holds, for each directory of every
work folder, the files filed right in it (their first folder, one read of
`idx_ub_dir`), which a folder's count sums down its subtree; through a
folder share only the folders it reaches. `work_changes` says which
directories were written lately: `seq` the workspace change log's last
(`page_changes`), `dirs` the last write to a file filed right in each
directory among the writes after `since` (the last 500 seqs; a folder
share's only for the folders it reaches), so a directory read at a seq
(`GET /folders/{id}/pages` answers it) of at least `since` is as its files
stand while `dirs` names no later write to it — a file renamed on disk
changes no count, and its page's write shows it. `seq` is the tree's op-log position, where a
client following the tree's room (`/ws/page/folders`, `/ws/page/labels`)
catches up from, like an open page's; the web app's home view does not join
the rooms — it reads the listing again after its own writes and when the
window comes back ([home_library.md](home_library.md) "Folders and labels").
Through a folder share the trees carry no `seq`:
`folders.children` is the shared folder's own node (with what is below it)
and `labels.children` the labels its pages carry.
`GET /blocks/{id}/subtree` on a page (or a tree) also returns `seq`, the
op-log position the tree reflects (the live session catches up from it).

in a work folder is judged by the work-folder rule. `GET /pages/{id}/export*` live
in `export.py`.

A build script can replace a page's PDF after each compile, with a
write-scope integration token ("Integrations and MCP" below) and the page's
id; the highlights follow their text into the new file
([highlight_relocation.md](highlight_relocation.md)). That run is the
token's account's `relocate-highlights` job, shown in the web app's
Background tasks; the token itself cannot read `/jobs` (403), though the
answer names the job. The simple way is the one-file client's `push`
([synced_vaults.md](synced_vaults.md#the-client)): it hashes the file, sends
it only when its bytes are not the page's already, waits for a build that
is still being written, and with `--watch` sends each new version.

```sh
python gamma_sync.py push build/main.pdf --page "$PAGE_ID" --server "$GAMMA_URL"   # the token from GAMMA_TOKEN
```

By hand, upload the file, then `PUT` its `doc_id`. Re-running it on an
unchanged file stores nothing new and changes nothing. `keep_old_days`
lets the build before go a day after nothing references it, instead of 30.

```sh
set -e  # a failed upload stops here, before the PUT
DOC=$(curl -fsS -H "Authorization: Bearer $GAMMA_TOKEN" -F file=@main.pdf "$GAMMA_URL/api/uploads" | jq -er .doc_id)
curl -fsS -X PUT -H "Authorization: Bearer $GAMMA_TOKEN" -H "Content-Type: application/json" \
  -d "{\"doc_id\": \"$DOC\", \"original_filename\": \"main.pdf\", \"keep_old_days\": 1}" "$GAMMA_URL/api/pages/$PAGE_ID/attachment"
```

"path", "work_folder", "format": "text", "language", "line", "lines":
[first, last], "snippet"}`: `title` the page's (a work folder's file's is

(`work_folders.paths.page_path`; `""` for a library text document),
`work_folder` the work folder's root id (`""` for a library document),
`language` the view's (`formats.language_of`), `line` the line the query
matched, `lines` the span of the run it is in, `snippet` that line cut
around the match. The line is found on the server by scanning the run's
lines with FTS5's own token rule (`documents.text.locate`: the query's
runs of letters and digits, each a whole word, the last a prefix), never
read off the snippet: `normalize_text` keeps a run's line breaks, not its
spaces. `GET /search` and `POST /document-search` build their hits, and
the agent's `search_library` its lines, through `search.hits.build`, the
one place the PDF and file dicts are made.

**The scope rule** (`routers/search.scope_pages`, both POSTs): `folders`
and `labels` resolve on the server through `pages_in_scope` (each chip's
pages, intersected, as `scope` of the GET forms), so a folder chip on a
work folder travels as one id and reaches its 20,000 files; with `pages`
too, the result is the scope's pages among `pages`; `pages` alone is
`pages`; none of them, the whole library. `pages` is what the panel's
listing-side predicates keep (`year:`, `author:`, `is:pinned`…), which the
server cannot evaluate. `POST /block-search` takes the same three fields.

The notes index is `block_fts` in pages.db, kept by triggers inside every
block write's own transaction ([user_db.md](user_db.md) "The notes index"):
every block inside a page, highlights included, never a page's own row. A
page in Recently deleted keeps its rows; `block_index.search_blocks` takes
the page ids the search reaches (the library, or the `scope` folder's) and
matches only those, in SQL, before the `limit`. Snippets come from FTS5's
`snippet()` over the normalized text. The document index (`text_fts` in
data.db, `gamma/search/index.py`) is the one built lazily: a row is a unit,
a PDF's page or a text file's run of 40 lines (`documents.text.RUN_LINES`;
the run's lines follow from its number), each at most 20,000 characters, so
bm25 ranks pages and runs together. Indexed are `pdf` and `text`
documents; never a Markdown file (its blocks are notes), a picture, a
recording, a binary file, a listed file, or a secrets file's text
(`documents.text.is_secret`: recorded with no text, as a PDF without a text
layer is, and a page whose name is a secrets file's now is no hit, whatever
its bytes were indexed as). One rule normalizes indexes and queries (`textnorm`), code
included: `f(1,2)` indexes as `f(12)`, which its query matches. FTS5 finds
rows only by rowid or MATCH, so `text_fts_rows` maps each document to its
rows' rowids: every delete goes by rowid, and `index.search` keeps to its
documents by their rowids, in SQL before the ranking and its `limit` /
`offset` (read off the matches, not looked up one rowid at a time, which a
prefix query makes slow). An index of another layout (an older Gamma's
`pdf_fts`) is dropped and made again, empty, on first use, and every
document indexes again lazily. Deleting a page for good, deleting a block
that carries a document or detaching one drops the rows and manifests of
documents no block carries (`index.purge_unused`); a replacement drops the
one hash it let go when no block owns it any more (`index.purge_doc`, one
indexed lookup). A search counts as pending the documents the index lacks,
less the linked files out of reach: which are linked is one query
(`storage.linked_names`), and at most `PROBE_LIMIT` (200) of them are
tested for reach per search. Extraction and the job are
`gamma/search/indexer.py` (documents written in batches of about 500 units
per transaction; a PDF at an address is read through the chat's guarded
resolver, `ai_context.pdf_path`, which downloads it when it is not stored).

#### Search matching and display

Search normalization lives in `gamma/textnorm.py` and its frontend mirror,
`shared/lib/textnorm.js`: ligatures, hyphenated line breaks, and digit
separators should match consistently. The extraction (`pdf_text`, through
PyMuPDF) hands over the page as it is — a hyphen at an end-of-line word
break stays, and a ligature comes out as its letters — and `textnorm` re-joins the word for the index and for
queries alike. Bump `textnorm.INDEX_VERSION` when
extraction or normalization changes so old indexes rebuild. Add shared cases
to `tests/shared/textnorm.json` and run both Python and Node coverage.

`search/SearchPanel.jsx` groups titles, the current page's notes and PDF,
other notes, reference links, library PDF hits and Files (the text files'
lines: a row names the file's directory and its line, and opens the code
view at that line, marked). It can collapse into a compact find bar. The
browser group `text-search` (`tests/e2e/scenarios/textSearch.mjs`) runs a
work folder's `.tex` files through the panel, the chat's line link, a
note's line pill and MCP.

The box takes qualifiers beside its text, parsed in the browser: the
grammar is `search/queryParse.js` (spaces AND, commas list alternatives, a
leading `-` excludes, quotes hold a value's spaces and commas; `：`, `，` and
smart quotes count; keys fold case), and Gamma's table is
`search/searchFilters.js` (`label:`, `folder:`, `is:pdf|pinned`,
`no:label|folder`, `author:`, `venue:`, `year:`, `created:`, `updated:`,
`in:`). Every key but `in:` keeps pages, and is evaluated against the
library listing (`GET /blocks/root/children`, which carries each page's
filing, pin, dates and paper metadata) through the same libraryUtils reads
as the label and folder chips. The chips are unchanged and combine with
the typed qualifiers. The chips, and a `folder:` or `label:` qualifier
naming one folder or label, go to `POST /block-search` and `POST
/document-search` as `folders` and `labels` (the scope rule above); a
negated one, or one naming several (`folder:a,b`, a name two folders
share), stays a predicate, since the server intersects the ids it is sent
and has no OR or NOT. The ids of the pages the predicates keep go as
`pages`, so the server ranks and limits inside them and a match
in the chosen folder is found however many elsewhere outrank it. The ids
travel in a body because a URL cannot carry them: the
iPad and Android servers run uvicorn on h11, whose request head stops at
16 KiB, and `-label:read` over 1,500 pages is already about 22 KB. Dates
resolve in the reader's local time, which the server does not know. A
search runs again when a listing refresh changes which pages match, and
when an indexing job ends while its answer counted documents not indexed
yet (App's `indexed`, the ended jobs' ids; again only while each answer
counts fewer, so a linked file out of reach, which stays pending, does not
start the job over and over), and a
"Show more" sends the ids its first page was asked with. `in:` picks the
groups (`title`, `notes`, `highlights`, `links`, `pdf`, `files`) and,
through `kinds`, the block kinds of the notes search and, through
`formats`, the documents' (`pdf`, `text`); a group left out sends no
request. The free text is the query with the applied qualifiers cut out;
with none it is the query as typed, so `3000` still finds `3,000-qubit`.
A token with an unknown key (`arXiv:2301.12345`, `doi:`, `10:30`) is text.
So is a known key whose value cannot be applied (`year:abc`, `is:foo`, a
label or folder name that does not exist), and an amber line says why: a
typo finds nothing or the literal text, never more than was asked for.

The groups start at 8 titles, 20 notes and 15 document hits (`DOC_PAGE`);
each has a "Show more" that appends the next page (`search/searchPages.js`):
the notes and document groups send the last answer's `next` back as `cursor`, and the titles,
matched in the browser, just show 8 more. A notes scan cut short by its 2 s
budget keeps its "stopped early" line, and its "Show more" goes on from
where it stopped. An answer for a search the panel has moved past (a new
query, flags or chips) is dropped. `buildSearchRegex` supplies the
frontend matcher; the server's `/block-search` uses its own bounded fuzzy
scan after an SQL prefilter and refuses caller-supplied regexes. There is
no replace UI.

Opening a library content hit pins the query across navigation. Once the PDF
renders, `PdfViewer` re-finds the query through `searchRef` over normalized
page text, maps character offsets back to rendered rectangles, and scrolls
to the match. Search indexes store text, not highlight coordinates: the
positions must come from pdf.js, which renders the page.

### Chats (`chats.py`, prefix `/api/chats`)

`GET /chats/{page_id}?share=<token>` exposes only the shared page's active
saved conversation, subject to the link's audience. Shared pages show this in
a read-only AI chat window on desktop and mobile, with search and copy.
Chat mutations reject share tokens, including links that allow page editing;
archived conversation browsing remains session-only. Every chat write takes
a workspace editor (`require_ws(write=True)`): a viewer or a read-scope
token reads chats and history, and gets 403 on each write below. The
conversations live in the workspace's pages.db (`chats`, `chat_history`,
keyed by `bucket`, [user_db.md](user_db.md)). A bucket is a block id — a
page's, or a folder's for the folder view's chat — or `home` (the library
root); a deleted folder's conversations are filed into `home`'s history by the
tree's `delete` op (`DELETE /folders/{id}`, or a tree batch).

another editor of the workspace gets 403, anyone else 404, and a file

The routes marked **P** take a path on this computer. A page of Gamma never
names one: the shell's native dialog does. So when the desktop app started
the server with a secret (`GAMMA_SHELL_SECRET`, new at each start,
`config.shell_secret`), a request to one of them must carry it as
`X-Gamma-Shell`, compared in constant time, or it gets 403. With no secret
(dev, tests) nothing is checked.
